## 디버깅, 왜 중요한가?

개발자가 실제 코드를 작성하는 시간은 전체 업무의 절반도 채 되지 않는다는 연구 결과가 있습니다. 나머지 절반은 기획 논의, 코드 리뷰, 그리고 **디버깅**에 쏟아집니다. 그럼에도 불구하고 디버깅 기술을 체계적으로 배우는 기회는 드뭅니다. 대부분은 `console.log`를 심어가며 경험으로 익힐 뿐이죠.

이 글에서는 효율적인 디버깅을 위한 7가지 실전 기법을 소개합니다. 이 기법들을 숙지하면 버그 해결 시간을 크게 단축하고, 더 나아가 버그가 생기기 어려운 코드를 작성하는 습관도 자연스럽게 생깁니다.

---

## 1. 재현하기: 버그의 절반은 재현에 있다

버그를 고치기 전에 반드시 **100% 재현**할 수 있어야 합니다. 재현할 수 없는 버그는 고쳤다고 착각하기 쉽습니다.

- 어떤 환경에서 발생하는가? (운영 체제, 브라우저, Node 버전)
- 어떤 데이터가 입력됐을 때 발생하는가?
- 어떤 순서로 조작했을 때 발생하는가?

재현 조건을 찾는 과정 자체가 버그의 원인을 좁혀주는 강력한 도구입니다.

---

## 2. 이진 탐색으로 원인 범위 좁히기

버그가 발생하는 코드가 어느 구간인지 모를 때, **이진 탐색(Binary Search)** 방식이 효과적입니다.

```javascript
// 예시: 1000줄짜리 데이터 변환 파이프라인에서 버그 발생
// 500번째 줄에 중간 결과를 출력해 범위를 절반으로 좁힘
console.log('[중간 확인]', intermediateResult);
```

Git을 사용하고 있다면 `git bisect` 명령을 활용하면 어떤 커밋에서 버그가 도입됐는지 자동으로 이진 탐색해줍니다.

```bash
git bisect start
git bisect bad          # 현재 커밋은 버그 있음
git bisect good v1.2.0  # 이 태그에서는 정상이었음
# 이후 git이 중간 커밋을 체크아웃 → 테스트 → bad/good 반복
```

---

## 3. console.log 보다 강력한 브라우저 DevTools 활용

`console.log`는 가장 빠른 디버깅 도구지만, 브라우저 DevTools의 **Breakpoint 디버거**를 사용하면 훨씬 깊이 파고들 수 있습니다.

### 브레이크포인트 종류

| 종류 | 사용법 | 용도 |
|------|--------|------|
| Line breakpoint | Sources 탭에서 줄 번호 클릭 | 특정 줄에서 실행 정지 |
| Conditional breakpoint | 우클릭 → "Add conditional breakpoint" | 조건 충족 시에만 정지 |
| XHR breakpoint | Sources → XHR/fetch Breakpoints | 특정 URL 요청 시 정지 |
| DOM breakpoint | Elements 탭 우클릭 | DOM 변경 시 정지 |

특히 **Conditional breakpoint**는 반복문 안에서 특정 값일 때만 멈추고 싶을 때 매우 유용합니다.

```javascript
// 조건부 브레이크포인트 예시 조건식:
user.id === 'problematic-user-id'
```

## 4. Node.js 환경에서의 디버깅

서버 사이드 코드는 브라우저 DevTools를 쓸 수 없습니다. 대신 다음 방법들을 활용하세요.

### `--inspect` 플래그로 Chrome DevTools 연결

```bash
node --inspect server.js
# 또는 이미 실행 중인 프로세스에 연결
node --inspect-brk server.js  # 첫 줄에서 멈추고 시작
```

Chrome에서 `chrome://inspect`로 접속하면 친숙한 DevTools 인터페이스로 서버 코드를 디버깅할 수 있습니다.

### VS Code 디버거 사용

`.vscode/launch.json`을 설정하면 VS Code에서 바로 디버깅 세션을 시작할 수 있습니다.

```json
{
  "type": "node",
  "request": "launch",
  "name": "Launch Program",
  "program": "${workspaceFolder}/server.js"
}
```

## 5. 에러 메시지를 끝까지 읽는 습관

놀랍게도 많은 개발자가 에러 메시지를 끝까지 읽지 않습니다. 스택 트레이스(Stack Trace)에는 버그의 위치와 호출 흐름이 고스란히 담겨 있습니다.

```
TypeError: Cannot read properties of undefined (reading 'name')
    at getUserName (utils.js:42:20)   ← 실제 에러 발생 위치
    at renderUserCard (Card.jsx:15:5) ← 호출한 곳
    at App (App.jsx:30:3)             ← 그 위
```

스택 트레이스를 위에서 아래로 읽되, **자신이 작성한 코드**가 등장하는 첫 번째 줄에 집중하세요. 라이브러리 내부 코드보다 내 코드의 호출 지점이 원인인 경우가 대부분입니다.

---

## 6. 가정을 테스트로 증명하기

"이 변수는 당연히 숫자겠지", "이 함수는 항상 배열을 반환하겠지"와 같은 **무근거한 가정**이 버그의 온상입니다. 가정을 의심하고 즉시 확인하세요.

```javascript
// 디버깅 중에 일시적으로 assertion 추가
function processItems(items) {
  console.assert(Array.isArray(items), '❌ items가 배열이 아님:', items);
  console.assert(items.length > 0, '❌ items가 비어있음');
  // ...
}
```

이 습관은 장기적으로 **방어적 프로그래밍(Defensive Programming)** 스타일로 이어지며, 버그가 아예 발생하지 않는 코드를 작성하는 데 도움이 됩니다.

---

## 7. 고무 오리 디버깅 (Rubber Duck Debugging)

가장 고전적이지만 놀랍도록 효과적인 방법입니다. 버그를 해결하기 위해 **다른 사람(혹은 고무 오리 인형)에게 코드를 처음부터 설명**해보세요.

설명하는 과정에서 다음과 같은 일이 일어납니다.

- "이 변수는 이렇게 동작한다고 생각했는데, 사실은..."
- "이 조건문 앞에서 항상 이 값이 온다고 전제했는데..."
- "아, 여기서 비동기 처리를 빠뜨렸네!"

혼자 해결이 안 될 때는 동료에게 도움을 구하기 전에 먼저 고무 오리에게 설명해보세요. 동료에게 설명하러 가는 도중 이미 답을 찾는 경우가 많습니다.

---

## 마무리: 디버깅을 두려워하지 마세요

디버깅은 고통스러운 과정이 아니라, 코드와 시스템을 **더 깊이 이해하는 기회**입니다. 버그 하나를 제대로 해결할 때마다 그 시스템에 대한 이해가 한 층 깊어집니다.

오늘 소개한 7가지 방법을 하나씩 실천해보세요.

1. **재현 먼저** — 완전한 재현이 해결의 시작
2. **이진 탐색** — 범위를 반씩 좁혀라
3. **DevTools 브레이크포인트** — `console.log`에서 한 단계 업
4. **Node.js 인스펙터** — 서버 코드도 GUI로 디버깅
5. **스택 트레이스 정독** — 에러 메시지는 이미 답을 알고 있다
6. **가정을 assertion으로** — 의심하고 증명하라
7. **고무 오리 디버깅** — 설명하는 순간 해결책이 보인다

꾸준히 연습하면 어느 순간 디버깅이 두렵지 않고 오히려 즐거운 탐정 놀이처럼 느껴질 것입니다.
