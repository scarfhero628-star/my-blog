## 코드 리뷰가 왜 중요한가?

코드 리뷰는 단순히 버그를 찾는 작업이 아닙니다. 팀의 코드 품질을 높이고, 지식을 공유하며, 서로의 성장을 돕는 협업의 핵심 과정입니다. 구글, 페이스북 같은 세계적인 기업들이 코드 리뷰를 필수로 여기는 데는 이유가 있습니다.

- **버그 조기 발견**: 테스트를 통과하더라도 로직 오류를 사람이 발견할 수 있습니다.
- **지식 공유**: 리뷰어는 코드베이스 전반을 이해하게 되고, 작성자는 새로운 관점을 얻습니다.
- **코드 일관성 유지**: 팀 전체가 같은 스타일과 패턴을 따르게 됩니다.
- **온보딩 단축**: 새로운 팀원이 코드 리뷰를 통해 팀의 컨벤션과 도메인 지식을 빠르게 흡수할 수 있습니다.

## 좋은 코드 리뷰를 주는 법

### 1. 작은 단위로 리뷰하기

리뷰할 코드가 너무 많으면 집중력이 흐려집니다. PR 하나에 200~400줄 이내가 이상적입니다. 큰 변경이 필요하다면 여러 PR로 나누도록 요청하거나, 먼저 설계를 리뷰하고 구현은 이후에 보는 방식을 제안해 보세요.

### 2. 설계를 먼저, 세부 구현은 나중에

세부 구현보다 전체 설계가 올바른지 먼저 확인하세요. 작은 오타를 지적하기 전에 방향이 맞는지를 먼저 확인하는 것이 효율적입니다. 설계 자체가 잘못됐다면 구현 세부사항 피드백은 대부분 의미가 없어집니다.

### 3. 명확하고 친절하게 피드백하기

```
# 나쁜 예
이 코드 왜 이렇게 짰어요?

# 좋은 예
이 부분에서 n+1 쿼리가 발생할 수 있어요.
include(:users)를 추가하면 성능이 개선될 것 같은데, 어떻게 생각하세요?
```

비판이 아닌 질문 형식으로 피드백을 주면 상대방이 방어적으로 반응하지 않습니다. "이렇게 해야 합니다"보다 "이렇게 하면 어떨까요?"가 훨씬 협업적인 표현입니다.

### 4. 칭찬도 아끼지 않기

좋은 점도 명시적으로 언급해 주세요. "이 부분 깔끔하게 구현하셨네요!" 한 마디가 팀 분위기를 크게 바꿉니다. 리뷰어가 문제점만 지적한다고 인식되면 PR 올리는 것 자체를 꺼리게 됩니다.

### 5. 우선순위를 명확히 하기

모든 의견이 동일한 중요도를 갖지 않습니다. "반드시 수정", "권장 사항", "개인적 선호" 등으로 구분하면 작성자가 무엇에 집중해야 할지 명확해집니다.

```
[필수] 이 함수에서 null 처리가 빠져 있어 런타임 에러가 발생합니다.
[권장] 변수명을 data 대신 userProfile로 바꾸면 의도가 더 명확해질 것 같습니다.
[선호] (제 취향이지만) 삼항 연산자보다 if문이 더 읽기 편할 것 같아요.
```

이 방식을 사용하면 리뷰어와 작성자 모두 무엇이 차단 요소(blocking)이고 무엇이 제안 사항인지 빠르게 파악할 수 있습니다.

### 6. 자신도 틀릴 수 있다는 걸 인정하기

리뷰어도 완벽하지 않습니다. "제가 놓친 부분이 있을 수도 있는데, 이 코드가 이렇게 동작하는 이유가 있나요?"처럼 열린 질문을 하면 더 좋은 대화가 됩니다.

## 코드 리뷰를 잘 받는 법

### 1. PR 설명을 충실하게 작성하기

리뷰어가 맥락을 빠르게 파악할 수 있도록 PR에 다음을 포함하세요:

- **변경 이유 (Why)**: 왜 이 변경이 필요한가?
- **무엇을 바꿨는지 (What)**: 어떤 부분을 어떻게 변경했는가?
- **테스트 방법 (How to test)**: 어떻게 확인할 수 있는가?
- **스크린샷**: UI 변경이 있다면 before/after 이미지를 첨부하세요.

좋은 PR 설명은 리뷰어의 시간을 절약해 주고, 더 집중된 피드백을 받을 수 있게 합니다.

### 2. 방어적으로 반응하지 않기

피드백은 코드에 대한 것이지, 당신에 대한 것이 아닙니다. "왜 이렇게 생각하셨나요?"라고 질문하거나 "좋은 지적이네요, 이 방향으로 수정해 보겠습니다"처럼 개방적인 자세가 훨씬 효과적입니다.

### 3. 반영 여부를 명확히 표시하기

피드백을 반영했는지, 아니면 왜 다르게 결정했는지를 댓글로 남겨두세요. 리뷰어 입장에서 어떤 의견이 받아들여졌는지 추적하기 어렵습니다.

```
# 반영한 경우
수정했습니다! null 체크를 추가했어요.

# 반영하지 않은 경우
좋은 의견 감사해요. 다만 현재 이 함수는 외부 API에서 항상 값이 내려오는 것을
보장하고 있어서 일단 이대로 두려고 합니다. 혹시 다른 의견 있으시면 알려주세요!
```

## 팀 코드 리뷰 문화 만들기

좋은 코드 리뷰 문화는 규칙이 아닌 **심리적 안전감**에서 시작됩니다. "실수해도 괜찮다", "배우면 된다"는 분위기가 먼저 만들어져야 사람들이 솔직한 피드백을 주고받을 수 있습니다.

팀에서 코드 리뷰 문화를 개선하고 싶다면:

1. **리뷰 응답 시간 합의**: "영업일 기준 24시간 내 응답" 같은 팀 규칙을 정해두세요. 기다림에 지쳐 리뷰를 포기하는 일이 없어야 합니다.
2. **자동화로 기계적인 부분 처리**: ESLint, Prettier 같은 도구로 코딩 스타일 지적을 줄이면 리뷰어가 비즈니스 로직과 설계에 집중할 수 있습니다.
3. **리뷰 칭찬 문화**: 특히 꼼꼼하고 친절한 리뷰를 한 팀원을 공개적으로 칭찬해 보세요.
4. **리뷰 가이드라인 문서화**: 팀 내에서 공통으로 따를 코드 리뷰 기준을 문서로 만들어 두면 개인 선호에 의한 의견 충돌이 줄어듭니다.

## 마무리

코드 리뷰는 기술적인 작업이자 인간적인 소통입니다. 기술적 정확성만큼이나 **어떻게 말하느냐**가 중요합니다. 오늘부터 리뷰에 칭찬 한 줄씩 더해보세요. 팀의 분위기와 코드 품질이 함께 달라질 것입니다.

코드 리뷰를 잘하는 것은 하루아침에 이루어지지 않습니다. 하지만 작은 실천 하나하나가 쌓여 팀 전체의 개발 문화를 바꾸는 큰 힘이 됩니다.
