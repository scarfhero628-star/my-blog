규모가 커진 서비스에서 "왜 배포 한 번에 이렇게 오래 걸리지?", "팀이 늘었는데 오히려 개발이 느려졌다"는 고민을 해본 적 있다면, 마이크로서비스 아키텍처가 해답이 될 수 있습니다. 이번 글에서는 마이크로서비스의 핵심 개념부터 모놀리스에서 전환하는 실전 전략까지 살펴봅니다.

## 모놀리스 아키텍처의 한계

처음 서비스를 만들 때는 모놀리식(Monolithic) 구조가 합리적입니다. 배포가 단순하고, 개발팀이 작을 때는 오히려 효율적입니다. 하지만 서비스가 성장하면서 문제가 생깁니다.

### 모놀리스의 대표적인 고통 포인트

- **느린 빌드·배포**: 코드 한 줄 바꿔도 전체를 새로 빌드·배포해야 합니다.
- **기술 스택 고착화**: 한 번 정한 언어·프레임워크를 전체가 따라야 합니다.
- **팀 간 충돌**: 여러 팀이 같은 코드베이스에서 작업하면 머지 충돌이 잦습니다.
- **확장성 제한**: 트래픽이 몰리는 특정 기능만 별도로 스케일아웃하기 어렵습니다.

## 마이크로서비스란 무엇인가

마이크로서비스는 하나의 큰 애플리케이션을 **비즈니스 도메인 단위의 작고 독립적인 서비스들**로 분리하는 아키텍처 스타일입니다. 각 서비스는 자체 데이터베이스를 갖고, API를 통해 통신하며, 독립적으로 배포됩니다.

```
모놀리스:
┌───────────────────────────────┐
│  사용자 / 주문 / 결제 / 알림  │
│         (하나의 앱)            │
└───────────────────────────────┘

마이크로서비스:
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ 사용자   │  │  주문    │  │  결제    │  │  알림    │
│ 서비스   │  │ 서비스   │  │ 서비스   │  │ 서비스   │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
     │              │              │              │
     └──────────────┴──────────────┴──────────────┘
                     API Gateway
```

## 마이크로서비스의 핵심 원칙

### 1. 단일 책임 원칙 (Single Responsibility)

각 서비스는 하나의 비즈니스 기능에만 집중해야 합니다. "주문 서비스"는 주문 생성·조회·취소만 담당하고, 결제는 별도 서비스에 위임합니다.

### 2. 데이터 독립성

서비스마다 전용 데이터베이스를 가져야 합니다. 다른 서비스의 DB에 직접 접근하는 것은 금물입니다.

```
❌ 잘못된 예: 주문 서비스가 결제 DB에 직접 쿼리
SELECT * FROM payment_db.payments WHERE order_id = ?

✅ 올바른 예: API 호출을 통한 간접 접근
GET /payments/search?orderId=12345
```

### 3. 느슨한 결합 (Loose Coupling)

서비스 간 의존성을 최소화합니다. 동기 HTTP 호출 대신 비동기 메시지 큐(Kafka, RabbitMQ)를 활용하면 한 서비스가 다운되어도 전체 시스템에 영향이 줄어듭니다.

## 서비스 간 통신 패턴

### 동기 통신 — REST / gRPC

```javascript
// 주문 서비스에서 결제 서비스 호출 (동기)
async function processOrder(orderId, amount) {
  const response = await fetch('http://payment-service/charge', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ orderId, amount }),
  });

  if (!response.ok) {
    throw new Error('결제 실패');
  }

  return response.json();
}
```

응답을 즉시 받아야 할 때 적합하지만, 결제 서비스가 느리거나 다운되면 주문 서비스도 영향을 받습니다.

### 비동기 통신 — 메시지 큐

```javascript
// 주문 완료 이벤트를 메시지 큐에 발행
async function completeOrder(order) {
  await db.orders.update({ id: order.id, status: 'COMPLETED' });

  // 알림 서비스, 포인트 서비스 등이 이 이벤트를 구독
  await messageQueue.publish('order.completed', {
    orderId: order.id,
    userId: order.userId,
    amount: order.amount,
  });
}
```

알림 서비스가 잠시 다운돼도 메시지가 큐에 쌓여 나중에 처리되므로 데이터 유실이 없습니다.

## API 게이트웨이 패턴

클라이언트가 수십 개의 서비스에 직접 접근하면 관리가 복잡해집니다. **API 게이트웨이**는 단일 진입점을 제공해 인증, 라우팅, 로드밸런싱, 요청 집계를 처리합니다.

```
클라이언트
    │
    ▼
API Gateway (인증, 라우팅, 속도 제한)
    ├── /users    → 사용자 서비스
    ├── /orders   → 주문 서비스
    └── /products → 상품 서비스
```

## 모놀리스에서 마이크로서비스로 전환하는 3단계

무조건 한 번에 전환하는 것은 위험합니다. **스트랭글러 피그(Strangler Fig) 패턴**을 활용하면 리스크를 줄일 수 있습니다.

### 1단계: 경계 식별

도메인 주도 설계(DDD)의 바운디드 컨텍스트를 기반으로 서비스 경계를 그립니다. 자주 변경되거나 독립 배포가 필요한 기능부터 분리 후보로 선정합니다.

### 2단계: 신규 기능은 마이크로서비스로

기존 모놀리스에 새 기능을 추가할 때 별도 서비스로 개발합니다. API 게이트웨이가 새 경로는 마이크로서비스로, 나머지는 모놀리스로 라우팅합니다.

### 3단계: 기존 기능 점진적 이관

트래픽이 많거나 독립 확장이 필요한 기능부터 순서대로 모놀리스에서 뽑아 별도 서비스로 이관합니다.

## 마이크로서비스의 현실적인 도전

마이크로서비스가 만능 해결책은 아닙니다. 다음 도전 과제를 미리 인지해야 합니다.

| 도전 과제 | 대응 방법 |
|-----------|-----------|
| 분산 트랜잭션 | Saga 패턴, 이벤트 소싱 |
| 서비스 디스커버리 | Kubernetes, Consul |
| 분산 로깅 | ELK 스택, Jaeger (분산 추적) |
| 서비스 장애 전파 | Circuit Breaker 패턴 |
| 테스트 복잡도 | 계약 테스트 (Pact) |

## 마이크로서비스가 맞는 상황인가?

팀 규모가 작고 서비스가 초기 단계라면 모놀리스가 더 낫습니다. **"먼저 잘 동작하는 모놀리스를 만들고, 실제로 필요해졌을 때 분리하라"**는 조언을 기억하세요.

마이크로서비스를 고려할 때는:
- 팀이 여러 개로 나뉘어 독립적으로 배포해야 할 때
- 특정 서비스만 집중적으로 스케일아웃이 필요할 때
- 서비스의 일부가 다른 기술 스택(예: ML 모델 서버)으로 개발돼야 할 때

## 마치며

마이크로서비스는 복잡성과 운영 비용을 감수하고 독립성과 확장성을 얻는 트레이드오프입니다. 은총알이 아니라 특정 문제를 해결하기 위한 도구임을 잊지 마세요. 작게 시작해서 필요에 따라 점진적으로 분리해 나가는 접근법이 가장 안전합니다.
