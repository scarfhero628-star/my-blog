소프트웨어 개발을 하다 보면 "일단 돌아가게만 만들자"는 결정을 내릴 때가 있습니다. 데드라인이 코앞이거나, 요구사항이 계속 바뀌거나, 아직 전체 그림이 보이지 않을 때입니다. 이렇게 쌓인 타협들이 바로 **기술 부채(Technical Debt)**입니다.

기술 부채라는 개념을 처음 제시한 워드 커닝엄(Ward Cunningham)은 이를 금융 부채에 빗대어 설명했습니다. 지금 당장 빌린 돈처럼 빠른 개발을 가능하게 해 주지만, 이자처럼 쌓이는 유지보수 비용이 결국 팀 전체의 발목을 잡습니다.

---

## 기술 부채의 유형

기술 부채를 무조건 나쁜 것으로 보는 시각은 단순합니다. 그 성격을 먼저 구분해야 효과적으로 대응할 수 있습니다.

### 의도적 부채

팀이 **알면서** 택한 타협입니다.

- MVP 출시를 위해 복잡한 에러 처리를 생략
- 프로토타입에서 하드코딩된 설정값
- 성능 최적화를 나중으로 미룬 단순한 구현

의도적 부채는 그 자체로 나쁘지 않습니다. 문제는 "나중에 고친다"는 계획이 실현되지 않을 때입니다.

### 의도치 않은 부채

팀이 **모르는 사이** 쌓인 부채입니다.

- 경험 부족으로 인한 설계 결함
- 비즈니스 요구사항이 바뀌며 의미가 달라진 추상화
- 외부 의존성의 보안 취약점이나 하위 호환성 파기

이 유형은 코드 리뷰, 정기 감사, 팀 내 지식 공유를 통해 줄일 수 있습니다.

---

## 기술 부채의 진짜 비용

기술 부채는 단순히 코드가 지저분해지는 문제가 아닙니다.

**속도 저하**: 복잡하게 얽힌 코드는 새로운 기능을 추가할 때 예상보다 훨씬 오래 걸리게 만듭니다. "이 부분만 건드리면 되는 줄 알았는데..."라는 경험은 누구나 있을 것입니다.

**버그 증가**: 이해하기 어려운 코드는 실수를 유발합니다. 같은 로직이 여러 곳에 중복되어 있다면, 한 곳을 고쳐도 다른 곳이 여전히 버그를 품고 있습니다.

**온보딩 비용**: 새 팀원이 복잡한 레거시 코드를 파악하는 데 몇 주씩 걸린다면, 그 시간 자체가 조직이 지불하는 이자입니다.

**사기 저하**: 개발자는 빠르게 성장하고 싶어 합니다. 항상 과거의 실수를 수습하는 데 시간을 써야 한다면, 번아웃이 가속됩니다.

## 기술 부채 측정하기

관리할 수 없는 것은 측정할 수도 없습니다. 다음 도구와 지표를 활용해 부채를 가시화하세요.

### 정적 분석 도구

```bash
# ESLint로 코드 품질 문제 감지
npx eslint src/ --format html -o eslint-report.html

# SonarQube로 종합 품질 측정 (Docker)
docker run -d --name sonarqube -p 9000:9000 sonarqube:lts-community
```

### 순환 복잡도(Cyclomatic Complexity)

함수의 분기가 많을수록 테스트하기 어렵고 버그가 숨기 쉽습니다. 복잡도 10 이상의 함수는 리팩토링 후보입니다.

```javascript
// 복잡도 높음 — 분기 7개
function calculateDiscount(user, cart, coupon) {
  if (!user) return 0;
  if (cart.total < 10000) return 0;
  if (coupon && coupon.expired) return 0;
  if (coupon && coupon.type === 'percent') {
    if (user.isPremium) return cart.total * 0.2;
    return cart.total * coupon.value;
  }
  if (user.isPremium) return 5000;
  return 1000;
}

// 개선 — 전략 패턴으로 분리
const discountStrategies = {
  couponPercent: (cart, coupon, user) =>
    cart.total * (user.isPremium ? 0.2 : coupon.value),
  premium: () => 5000,
  default: () => 1000,
};
```

### 커버리지와 테스트 비율

테스트 커버리지가 낮은 모듈일수록 변경이 두렵습니다. 그 두려움 자체가 부채의 증거입니다.

## 기술 부채 관리 전략

### 1. 보이지 않는 것을 보이게 만들기

기술 부채는 이슈 트래커에 명시적으로 등록해야 합니다. "언젠가 고쳐야지"라는 구두 약속은 사라지지만, 이슈로 등록된 부채는 우선순위를 매길 수 있습니다.

```
제목: [기술부채] UserService 클래스 분리 필요
라벨: tech-debt, priority-medium
설명:
  - 현재 상황: UserService가 인증, 프로필, 알림을 모두 처리 (500줄)
  - 발생 비용: 인증 관련 버그 수정 시 프로필 로직도 파악해야 함
  - 제안: AuthService, ProfileService로 분리
  - 예상 소요: 1~2 스프린트
```

### 2. 보이 스카우트 원칙

> "언제나 처음 왔을 때보다 캠프장을 더 깨끗하게 만들고 떠나라."

새 기능을 추가하거나 버그를 수정할 때, 작업 범위 안에 있는 작은 부채는 그 자리에서 청산합니다. 의미 없는 변수명, 중복된 로직, 사용하지 않는 import 등을 정리하는 습관입니다.

단, **범위 크리프(scope creep)**를 주의해야 합니다. "이 김에 여기도 고치자"가 반복되면 PR이 거대해지고, 리뷰가 어려워집니다.

### 3. 부채 상환 시간 확보하기

많은 팀이 스프린트 용량의 10~20%를 기술 부채 상환에 할당합니다. 이 시간이 없으면 부채는 기하급수적으로 불어납니다.

| 방식 | 장점 | 단점 |
|------|------|------|
| 스프린트 내 20% 할당 | 꾸준한 개선 | 비즈니스 압박 시 쉽게 삭감 |
| 별도 리팩토링 스프린트 | 집중적 개선 가능 | 기능 개발 공백 발생 |
| 기능과 묶어서 처리 | 가시적 효과 | 범위 산정 어려움 |

### 4. 리팩토링의 황금률

리팩토링은 **동작을 바꾸지 않고 구조를 개선하는 것**입니다. 테스트 없이 리팩토링하면 버그를 심는 것과 같습니다.

```javascript
// 리팩토링 전: 테스트 먼저 작성
test('calculateDiscount returns 20% for premium users with percent coupon', () => {
  const user = { isPremium: true };
  const cart = { total: 50000 };
  const coupon = { type: 'percent', value: 0.1, expired: false };
  expect(calculateDiscount(user, cart, coupon)).toBe(10000);
});

// 테스트가 통과하면 리팩토링 시작
```

## 팀 문화로 만드는 부채 예방

기술 부채는 개인의 문제가 아니라 팀의 문제입니다. 가장 효과적인 예방책은 문화입니다.

**Definition of Done에 품질 기준 포함**: "기능이 동작한다"를 완료 조건으로 삼지 않습니다. 테스트 작성, 린트 통과, 코드 리뷰 완료를 완료의 정의에 넣으세요.

**심리적 안전감**: "빠르게 해야 하니 일단 넘어가자"는 압박이 부채를 만듭니다. 팀원이 "이 부분이 나중에 문제가 될 것 같다"고 말할 수 있는 환경이 필요합니다.

**정기 코드 건강 점검**: 분기마다 주요 모듈의 복잡도, 커버리지, 의존성을 함께 살펴보는 세션을 가집니다. 부채를 개인의 실수가 아니라 시스템의 현상으로 바라보는 시각을 공유합니다.

---

## 마치며

기술 부채는 완전히 없애는 것이 목표가 아닙니다. 적절한 부채는 오히려 팀의 속도를 높여주는 도구입니다. 중요한 것은 **부채를 인식하고, 측정하고, 의식적으로 관리하는 것**입니다.

"나중에 고치자"가 실제로 실행되는 팀은, 지금 당장의 압박에서도 장기적으로 더 빠르게 달릴 수 있습니다. 기술 부채는 무서운 적이 아니라, 잘 관리하면 팀의 성숙도를 보여주는 지표입니다.
