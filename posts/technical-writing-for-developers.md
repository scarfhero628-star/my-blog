## 왜 개발자에게 글쓰기가 중요한가?

대부분의 개발자는 코드 실력만 뛰어나면 된다고 생각하기 쉽습니다. 하지만 실제 현장에서 뛰어난 개발자일수록 글쓰기를 중요하게 여깁니다. PR 설명, 기술 문서, 팀 내 제안서, 블로그 포스트까지 — 글쓰기는 개발자의 영향력을 직접적으로 결정하는 도구입니다.

좋은 코드를 작성하는 것만큼이나 그 코드를 설명하는 능력이 팀의 신뢰와 프로젝트 성공에 기여합니다. 특히 원격 근무 환경에서는 대면 커뮤니케이션 대신 문서로 소통하는 경우가 많아, 글쓰기 역량이 더욱 부각됩니다.

글쓰기를 잘하는 개발자는 다음과 같은 이점을 누립니다:

- 코드 리뷰에서 의도를 명확히 전달해 불필요한 오해를 줄임
- 팀 내 문서가 풍부해져 온보딩 속도 향상
- 기술 블로그를 통해 개인 브랜드를 쌓고 커리어 기회 확대
- 사내 기술 제안이 의사 결정권자를 더 쉽게 설득

## 기술 글쓰기의 핵심 원칙

### 1. 독자를 먼저 정의하라

글을 쓰기 전에 항상 "이 글은 누구를 위한 것인가?"를 물어보세요.

- **팀 동료를 위한 내부 문서**: 기술 용어 사용 가능, 배경 설명 생략 가능
- **외부 개발자를 위한 API 문서**: 기본 개념부터 설명, 실행 가능한 예제 코드 필수
- **비개발자를 위한 기획 문서**: 전문 용어 최소화, 비유와 시각 자료 활용

독자에 따라 쓰는 방식이 완전히 달라집니다. 막연히 "모두를 위한 글"을 쓰려다 보면 아무에게도 도움이 안 되는 글이 됩니다.

### 2. 구조를 먼저 잡고 내용을 채워라

좋은 글은 좋은 코드와 닮아 있습니다. 함수를 짜기 전에 인터페이스를 먼저 설계하듯, 글도 전체 구조를 먼저 잡고 세부 내용을 채우세요.

```
# 기술 문서 구조 예시
1. 요약 (TL;DR) — 한 문장으로 핵심 전달
2. 배경 — 왜 이 문서가 필요한가
3. 본론 — 실제 내용과 예시
4. 결론 / 다음 단계 — 독자가 무엇을 해야 하는가
```

처음부터 완벽한 문장을 쓰려 하지 마세요. 개요를 먼저 잡은 뒤 살을 붙이는 방식이 훨씬 효율적입니다.

### 3. 능동태를 사용하라

수동태 문장은 읽기 어렵고 책임 소재가 불분명해집니다.

| 수동태 (피해야 할 예) | 능동태 (권장 예) |
|---|---|
| 해당 기능은 구현될 예정입니다 | 저희 팀이 다음 스프린트에 구현합니다 |
| 버그가 수정되었습니다 | Alice가 버그를 수정했습니다 |
| 설정이 변경될 수 있습니다 | 관리자가 설정을 변경할 수 있습니다 |

능동태를 사용하면 문장이 간결해지고 의도와 주체가 분명해집니다.

### 4. 구체적인 예시를 들어라

추상적인 설명보다 구체적인 예시가 훨씬 효과적입니다.

❌ "이 함수는 입력값을 검증합니다."

✅ "이 함수는 이메일 형식이 올바른지 확인합니다."

```js
// 예: 이메일 검증
validate('user@example.com')  // → true
validate('invalid-email')     // → false
```

코드 문서라면 항상 실행 가능한 예제 코드를 포함하세요. 말보다 코드가 더 많은 것을 설명합니다.

### 5. 짧고 명확한 문장을 쓰라

한 문장에 하나의 생각만 담으세요. 문장이 길어지면 접속사로 끊거나 두 문장으로 나누세요.

- **긴 문장**: "이 라이브러리는 다양한 기능을 제공하며 특히 성능 최적화에 초점을 맞추고 있어서 대용량 데이터를 처리할 때 유용하게 활용될 수 있습니다."
- **개선**: "이 라이브러리는 성능 최적화에 특화되어 있습니다. 대용량 데이터 처리에 적합합니다."

## 실전 글쓰기 루틴

### PR 설명 잘 쓰는 법

PR 설명은 코드 리뷰어를 위한 안내서입니다. 다음 구조를 따르면 효과적입니다:

```markdown
## 변경 사항
- 로그인 API 응답 시간 개선 (평균 300ms → 80ms)
- Redis 캐싱 레이어 추가

## 변경 이유
기존 API가 매번 DB를 조회해 응답 속도가 느렸습니다.
캐시 TTL은 5분으로 설정했습니다.

## 테스트 방법
1. 로컬에서 `npm test` 실행
2. /api/login 엔드포인트 응답 시간 확인
3. Redis 캐시 히트율 모니터링 대시보드 확인
```

좋은 PR 설명은 리뷰어가 코드를 보지 않아도 변경 의도를 이해할 수 있게 합니다.

### 기술 블로그 글쓰기

블로그 포스트는 처음 접하는 독자가 이해할 수 있도록 쓰세요.

- **제목**: 독자가 얻을 것을 명확히 명시
  - ❌ "React에서 상태 관리하기"
  - ✅ "Redux 없이 전역 상태를 관리하는 3가지 방법"
- **도입부**: 이 글이 필요한 이유, 읽고 나면 무엇을 알게 되는지 설명
- **본문**: h2/h3 제목으로 스캔 가능하게 구성
- **마무리**: 핵심 요약 + 독자가 취할 다음 행동

### README 작성법

오픈소스 프로젝트의 첫인상은 README입니다. 5분 안에 실행해 볼 수 없으면 많은 개발자가 떠납니다.

좋은 README의 구성:

1. **프로젝트 한 줄 설명** — 무엇을 하는 툴인가?
2. **빠른 시작 (Quick Start)** — 설치부터 첫 실행까지
3. **주요 기능** — 왜 이 툴을 써야 하는가, 다른 도구와의 차별점
4. **기여 방법** — 어떻게 참여할 수 있는가

```bash
# Quick Start 예시
npm install my-awesome-lib
```

```js
import { greet } from 'my-awesome-lib';
console.log(greet('World')); // "Hello, World!"
```

## 글쓰기를 향상시키는 습관

### 많이 읽어라

좋은 글쓰기는 좋은 글 읽기에서 시작합니다. 매주 기술 블로그 글 2-3편을 읽으면서 문장 구조, 설명 방식, 예시 활용법을 의식적으로 관찰하세요.

참고하면 좋은 글쓰기 자료:

- **MDN Web Docs** — 정확하고 명확한 기술 문서의 교과서
- **Google Developer Documentation Style Guide** — 기술 문서 작성의 표준
- 유명 오픈소스 프로젝트의 `CONTRIBUTING.md` — 기여자 가이드 작성법 참고

### 초고를 빠르게 쓰고, 수정에 집중하라

"완벽한 첫 문장"을 찾으려다 아무것도 못 쓰는 경우가 많습니다. 일단 생각나는 대로 거칠게 쓴 다음, 다음 날 다시 읽으며 수정하세요. 시간적 거리는 객관적인 시각을 줍니다.

글쓰기도 코드처럼 리팩토링이 필요합니다. 첫 번째 커밋이 완벽할 필요는 없습니다.

### 글을 소리 내어 읽어보라

수정할 때 글을 소리 내어 읽어보면 어색한 표현, 너무 긴 문장, 문맥이 끊기는 부분을 금방 찾을 수 있습니다. 자연스럽게 읽히지 않으면 독자도 걸립니다.

### 피드백을 구하라

동료에게 "이 문서가 이해되나요?"라고 물어보는 것은 코드 리뷰를 요청하는 것과 같습니다. 작성자 본인은 내용을 이미 알고 있어서 놓치는 부분을 독자가 잡아줍니다.

## 마치며

코딩과 글쓰기는 생각을 정확히 표현하는 도구라는 점에서 닮아 있습니다. 좋은 코드는 스스로를 설명하고, 좋은 글은 아이디어를 정확히 전달합니다.

오늘 당장 모든 것을 바꿀 필요는 없습니다. PR 설명 한 줄을 조금 더 명확하게 써보는 것부터 시작하세요. 작은 습관이 쌓이면 어느 순간 팀에서 "글 잘 쓰는 개발자"로 불리게 될 것입니다.
