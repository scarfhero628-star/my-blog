## 왜 오픈소스 기여를 해야 할까?

많은 개발자들이 오픈소스 기여를 막연하게 어렵고 거창한 일로 생각합니다. 하지만 오픈소스 기여는 단순히 유명 프로젝트에 핵심 기능을 추가하는 것만을 의미하지 않습니다. 오타 수정, 문서 개선, 테스트 추가 등 작은 기여도 모두 소중한 기여입니다.

오픈소스 기여를 통해 얻을 수 있는 것들은 다음과 같습니다.

- **실력 향상**: 실제로 수많은 사람들이 사용하는 코드를 읽고 개선하면서 빠르게 성장합니다
- **포트폴리오 강화**: GitHub에 남는 기여 기록은 훌륭한 포트폴리오가 됩니다
- **네트워킹**: 전 세계 개발자들과 협업하며 인맥을 쌓을 수 있습니다
- **커뮤니티 기여**: 자신이 사용하는 도구를 더 나은 방향으로 발전시키는 보람이 있습니다

---

## 기여할 프로젝트 찾기

### 1. 내가 이미 쓰는 도구부터 시작하기

가장 좋은 시작점은 평소에 자신이 직접 사용하는 라이브러리나 도구입니다. 사용하다 불편한 점이나 문서의 오류를 발견했다면 그것이 바로 기여의 출발점이 됩니다.

### 2. Good First Issue 레이블 활용하기

GitHub에서는 초보자를 위해 `good first issue` 또는 `beginner-friendly` 레이블이 붙은 이슈를 제공하는 경우가 많습니다. 이런 이슈는 프로젝트 초보자도 해결할 수 있도록 범위가 명확하게 제한되어 있습니다.

```
# GitHub 검색창에서 다음과 같이 검색해 보세요
label:"good first issue" language:JavaScript
label:"good first issue" language:Python is:open
```

### 3. 유명 플랫폼 활용하기

- **[firstcontributions.github.io](https://firstcontributions.github.io)**: 오픈소스 기여 연습 전용 저장소
- **[up-for-grabs.net](https://up-for-grabs.net)**: 기여자를 찾는 프로젝트 목록
- **[goodfirstissue.dev](https://goodfirstissue.dev)**: 언어별로 Good First Issue를 모아 보여주는 사이트

## 기여 프로세스 단계별 가이드

### 1단계: 저장소 포크(Fork)하기

기여하고 싶은 프로젝트를 발견했다면, 먼저 해당 저장소를 자신의 GitHub 계정으로 포크합니다. 포크는 원본 저장소의 완전한 복사본을 내 계정 아래에 만드는 작업입니다.

### 2단계: 로컬에 클론하기

```bash
# 포크한 저장소를 로컬에 클론
git clone https://github.com/내-아이디/저장소이름.git
cd 저장소이름

# 원본 저장소를 upstream으로 추가
git remote add upstream https://github.com/원본-아이디/저장소이름.git
```

### 3단계: 작업 브랜치 만들기

```bash
# 최신 상태로 업데이트
git fetch upstream
git checkout main
git merge upstream/main

# 새 브랜치 생성
git checkout -b fix/typo-in-readme
```

브랜치 이름은 작업 내용을 명확하게 나타내도록 짓는 것이 좋습니다. `fix/`, `feat/`, `docs/` 등의 접두사를 활용하면 다른 기여자들이 브랜치의 목적을 쉽게 파악할 수 있습니다.

### 4단계: 변경사항 작성 및 커밋

코드를 수정한 후, 변경사항을 커밋합니다. 커밋 메시지는 영어로 작성하는 것이 일반적이며, 프로젝트의 기존 커밋 스타일을 따르는 것이 좋습니다.

```bash
git add .
git commit -m "fix: correct typo in README.md"
git push origin fix/typo-in-readme
```

### 5단계: Pull Request 열기

포크한 저장소의 GitHub 페이지에서 `Compare & pull request` 버튼을 클릭합니다. PR 설명에는 다음 내용을 포함하면 좋습니다.

- **무엇을 변경했는가**: 구체적인 변경 내용 설명
- **왜 변경했는가**: 변경의 이유나 해결하는 문제
- **어떻게 테스트했는가**: 변경사항을 확인하는 방법
- **관련 이슈**: `Closes #123` 형태로 관련 이슈 연결

## 첫 기여에서 자주 하는 실수

### 이슈 없이 PR을 보내는 것

규모가 있는 기능 변경이나 버그 수정은 먼저 이슈를 열어 메인테이너와 방향을 확인한 후 PR을 여는 것이 좋습니다. 아무도 리뷰하지 않을 큰 PR을 오랫동안 작성하는 낭비를 피할 수 있습니다.

### PR 범위를 너무 넓게 잡는 것

첫 기여는 작을수록 좋습니다. 한 번에 너무 많은 것을 바꾸려 하면 리뷰어가 검토하기 어렵고, 머지까지 시간이 오래 걸립니다.

### 기여 가이드라인을 읽지 않는 것

대부분의 프로젝트에는 `CONTRIBUTING.md` 파일이 있습니다. 이 파일에는 코딩 스타일, 커밋 메시지 형식, 테스트 방법 등 중요한 규칙이 담겨 있습니다.

```bash
# 기여 가이드라인 파일 확인
cat CONTRIBUTING.md
cat .github/CONTRIBUTING.md
```

## 리뷰 피드백 대응하기

PR을 열면 메인테이너나 다른 기여자가 코드 리뷰를 남길 수 있습니다. 피드백을 받으면 다음과 같이 대응하세요.

1. **열린 마음으로 받아들이기**: 리뷰어는 프로젝트를 더 좋게 만들려는 목적으로 피드백을 남깁니다
2. **질문하기**: 이해가 안 되는 피드백은 정중하게 질문해 명확히 이해하세요
3. **수정 후 다시 커밋**: 피드백을 반영한 후 같은 브랜치에 커밋을 추가하면 PR이 자동으로 업데이트됩니다
4. **감사 표현하기**: 리뷰어의 시간을 내어준 것에 감사를 표현하는 것은 커뮤니티 분위기를 좋게 만듭니다

## 시작은 지금 당장

오픈소스 기여는 거창한 계획이 필요 없습니다. 지금 사용하고 있는 라이브러리의 README를 읽다가 오타를 발견했다면, 바로 오늘 첫 PR을 열어보세요. 작은 기여 하나가 여러분의 개발자 커리어에 큰 전환점이 될 수 있습니다.

첫 PR이 머지되는 순간의 기쁨은 직접 경험해봐야 알 수 있습니다. 지금 바로 시작해 보세요!
