## 왜 사이드 프로젝트를 해야 할까?

많은 개발자들이 "언젠가 나만의 프로젝트를 만들어 보겠다"고 다짐하지만, 실제로 완성까지 가는 경우는 드뭅니다. 그럼에도 불구하고 사이드 프로젝트는 개발자에게 굉장히 중요한 경험입니다.

**사이드 프로젝트가 주는 가치:**

- **실전 경험**: 회사 프로젝트에서 쓰기 어려운 새로운 기술을 직접 적용해볼 수 있습니다.
- **포트폴리오 강화**: 채용 담당자나 클라이언트에게 보여줄 수 있는 구체적인 결과물이 생깁니다.
- **수익 가능성**: 잘 만들어진 사이드 프로젝트는 추가 수입으로 이어지기도 합니다.
- **문제 해결 능력 향상**: 기획부터 배포까지 모든 과정을 혼자 처리하면서 엔지니어링 전반을 이해하게 됩니다.
- **동기 부여**: 본업과 별개로 내가 원하는 것을 만드는 경험 자체가 개발 의욕을 높여줍니다.

## 1단계: 아이디어 발굴하기

가장 큰 첫 번째 장벽은 "무엇을 만들지" 결정하는 일입니다.

### 좋은 아이디어를 찾는 세 가지 질문

1. **내가 불편함을 느끼는 것이 있는가?** — 가장 강력한 아이디어 소스입니다. 직접 겪는 불편함은 사용자 니즈와 직결됩니다.
2. **기존 도구로는 해결되지 않는 나만의 워크플로우가 있는가?** — 내가 반복적으로 수동으로 하는 작업은 자동화 도구의 씨앗이 됩니다.
3. **내 주변 사람들이 자주 하는 질문이나 요청이 있는가?** — 주변에서 반복되는 니즈는 더 넓은 시장의 신호일 수 있습니다.

### 아이디어 검증하기

아이디어를 무작정 개발하기 전에 먼저 검증하는 것이 중요합니다.

```
검증 체크리스트:
✅ 나 자신이 이 도구를 실제로 사용할 것인가?
✅ 비슷한 솔루션이 이미 있는가? (있다면 내 것의 차별점은?)
✅ 2~4주 안에 MVP를 만들 수 있는 규모인가?
✅ 기술적으로 내가 구현 가능한가?
```

## 2단계: 범위 설정 — 작게 시작하기

사이드 프로젝트가 실패하는 가장 흔한 이유는 **범위를 너무 크게 잡는 것**입니다.

### MVP(최소 기능 제품) 정의

MVP는 핵심 가치를 전달하는 가장 단순한 버전입니다. "있으면 좋은 기능"을 모두 제거하고, 반드시 있어야만 의미가 있는 기능 하나만 집중하세요.

**나쁜 예:**
> "사용자 로그인, 소셜 공유, 알림, 다크모드, 대시보드, 모바일 앱까지 다 갖춘 완벽한 버전"

**좋은 예:**
> "URL을 입력하면 요약을 보여주는 웹 페이지 하나"

### 기능 우선순위 정하기

```
Must Have (MVP에 필수)
  └─ 없으면 제품이 동작하지 않는 기능

Should Have (1차 업데이트)
  └─ 있으면 훨씬 좋지만 나중에 추가 가능

Nice to Have (언젠가)
  └─ 여유가 있을 때 추가할 기능
```

## 3단계: 기술 스택 선택

사이드 프로젝트에서 기술 스택을 고를 때는 두 가지 전략 중 하나를 선택하세요.

### 전략 A: 익숙한 기술로 빠르게 출시

새로운 것을 배우기보다 이미 잘 아는 기술로 빠르게 결과물을 만드는 방법입니다. 비즈니스 아이디어 검증이 목적이라면 이 전략이 유리합니다.

### 전략 B: 배우고 싶은 기술로 성장하기

새 기술을 배우는 것 자체가 목적이라면, 사이드 프로젝트는 최고의 학습 환경입니다. 단, 기술 학습과 제품 완성이라는 두 마리 토끼를 동시에 잡으려 하면 둘 다 놓칠 수 있습니다. 목적을 명확히 하세요.

```javascript
// 예: 간단한 Node.js + Express로 빠르게 프로토타입
const express = require('express');
const app = express();

app.get('/summarize', async (req, res) => {
  const { url } = req.query;
  const summary = await fetchAndSummarize(url);
  res.json({ summary });
});

app.listen(3000, () => console.log('MVP running!'));
```

## 4단계: 꾸준히 진행하기 — 번아웃 방지

사이드 프로젝트는 대부분 취미처럼 시작하지만, 의무감이 생기면서 금방 지쳐버리기 쉽습니다.

### 지속 가능한 루틴 만들기

- **고정된 작업 시간 설정**: 매일 1시간보다 주 3회 2시간이 더 효과적일 수 있습니다. 자신의 패턴을 파악하세요.
- **작은 커밋의 힘**: 매 작업마다 커밋을 남기면 진행 상황이 가시화되고 동기 부여가 됩니다.
- **"완벽"을 적으로 삼지 말기**: 동작하는 코드가 완벽한 코드보다 100배 낫습니다.

### 중단 위기를 넘기는 법

> "2주 동안 건드리지 않았다면, 프로젝트가 죽은 게 아니라 잠시 쉬고 있는 것입니다."

다시 시작하기 가장 쉬운 방법은 가장 간단한 작업부터 하는 것입니다. 버그 하나 고치기, 타입 하나 추가하기. 그 첫 커밋이 모멘텀을 되살립니다.

## 5단계: 출시와 공유

많은 개발자들이 "조금 더 완성하고 나서 공개하겠다"며 미루다 결국 출시를 못 합니다.

### 출시 전 최소 체크리스트

```
배포 준비 체크리스트:
✅ 핵심 기능이 오류 없이 동작하는가?
✅ 기본적인 에러 처리가 되어 있는가?
✅ README 또는 간단한 사용법 설명이 있는가?
✅ 도메인 또는 공개 URL이 있는가?
```

### 공유할 수 있는 채널

- **GitHub**: 코드 공개로 개발자 커뮤니티에 노출
- **Product Hunt**: 프로덕트 출시 커뮤니티
- **개발자 커뮤니티**: OKKY, 개발자 Slack/Discord, Reddit r/webdev
- **트위터/X, LinkedIn**: 개인 SNS에서 개발 과정 공유 (Build in public)
- **기술 블로그**: 개발 과정에서 배운 것을 글로 쓰면 프로젝트와 본인 모두 홍보 효과

## 성공적인 사이드 프로젝트를 위한 마인드셋

사이드 프로젝트의 "성공"은 수익이나 사용자 수로만 측정되지 않습니다.

- 새로운 기술을 익혔다면 성공
- 완성품을 하나 더 포트폴리오에 추가했다면 성공
- 중간에 그만뒀더라도 그 과정에서 배운 게 있다면 성공

중요한 것은 **시작하고, 완성하고, 공유하는 것**입니다. 처음부터 완벽할 필요는 없습니다. 지금 바로 첫 번째 커밋을 만들어보세요.
