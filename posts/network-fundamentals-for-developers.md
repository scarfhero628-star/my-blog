웹 개발을 하다 보면 "API 응답이 왜 이렇게 느리지?", "CORS 에러는 왜 나는 거지?", "DNS는 도대체 어떻게 작동하는 거야?"라는 질문을 마주치게 됩니다. 프레임워크와 라이브러리만 잘 써도 개발은 가능하지만, 네트워크의 기초를 이해하면 디버깅 속도가 훨씬 빨라지고 성능 문제의 근본 원인을 짚어낼 수 있습니다. 이 글에서는 개발자가 반드시 알아야 할 네트워크 핵심 개념을 실무 관점에서 정리합니다.

## 왜 개발자가 네트워크를 알아야 하는가

현대 애플리케이션은 대부분 네트워크 위에서 동작합니다. 프론트엔드 개발자라면 HTTP 요청 최적화와 CORS 이해가 필수고, 백엔드 개발자라면 TCP 연결 관리, 로드 밸런싱, 타임아웃 설정 등을 다뤄야 합니다. 네트워크 지식이 부족하면 다음과 같은 상황에서 막히게 됩니다:

- 왜 첫 번째 HTTP 요청이 항상 느린지 이해 못함 (TCP 핸드셰이크 비용)
- DNS 캐시 문제로 배포 후에도 구 버전이 뜨는 원인을 모름
- `curl` 명령어로 API를 테스트할 때 헤더를 어떻게 붙여야 할지 모름
- TLS 인증서 오류가 왜 나는지 판단 못함

## OSI 7계층 모델: 네트워크를 이해하는 지도

네트워크를 공부할 때 가장 먼저 나오는 개념이 **OSI 7계층 모델**입니다. 복잡한 네트워크 통신을 7개의 계층으로 나눠 각 역할을 명확히 정의한 것입니다.

| 계층 | 이름 | 역할 | 프로토콜/장비 |
|------|------|------|---------------|
| 7 | 응용 계층 | 사용자와 직접 맞닿는 서비스 | HTTP, FTP, DNS |
| 6 | 표현 계층 | 데이터 인코딩·암호화 | TLS/SSL |
| 5 | 세션 계층 | 세션 연결과 종료 관리 | — |
| 4 | 전송 계층 | 신뢰성 있는 데이터 전달 | TCP, UDP |
| 3 | 네트워크 계층 | 경로 설정 (라우팅) | IP, ICMP |
| 2 | 데이터 링크 계층 | 같은 네트워크 내 통신 | Ethernet, MAC |
| 1 | 물리 계층 | 전기 신호 전달 | 케이블, 허브 |

실무에서는 주로 **3계층(IP), 4계층(TCP/UDP), 7계층(HTTP)**을 중심으로 이해하면 충분합니다.

## TCP/IP: 인터넷의 근간

### IP 주소와 라우팅

IP(Internet Protocol)는 패킷을 목적지까지 전달하는 역할을 합니다. IPv4는 `192.168.1.1`처럼 4개의 8비트 숫자로 이루어지고, IPv6는 128비트를 사용합니다.

- **공인 IP**: 인터넷에서 고유하게 식별되는 주소 (예: 웹 서버 주소)
- **사설 IP**: 내부 네트워크에서만 쓰이는 주소 (`192.168.x.x`, `10.x.x.x`)
- **NAT**: 사설 IP를 공인 IP로 변환하는 기술

### TCP 3-way 핸드셰이크

TCP(Transmission Control Protocol)는 연결을 맺기 전에 반드시 3단계 과정을 거칩니다. 이 과정이 HTTP 요청의 초기 지연(latency)에 영향을 미칩니다.

```
클라이언트                     서버
   |                            |
   |------- SYN --------------->|  (연결 요청)
   |<------ SYN-ACK ------------|  (요청 수락)
   |------- ACK --------------->|  (확인)
   |                            |
   |   ← 이제 데이터 전송 가능 →   |
```

1. **SYN**: 클라이언트가 서버에 연결을 요청
2. **SYN-ACK**: 서버가 수락하며 응답
3. **ACK**: 클라이언트가 최종 확인

이 세 번의 왕복(1.5 RTT) 때문에 첫 연결은 항상 추가 지연이 발생합니다. HTTP/2의 멀티플렉싱이나 QUIC(HTTP/3) 프로토콜은 이 문제를 완화하기 위해 등장했습니다.

### TCP vs UDP

| 항목 | TCP | UDP |
|------|-----|-----|
| 연결 | 연결 지향 (3-way handshake) | 비연결 |
| 신뢰성 | 보장 (재전송, 순서 보장) | 미보장 |
| 속도 | 상대적으로 느림 | 빠름 |
| 활용 | HTTP, HTTPS, FTP | 동영상 스트리밍, DNS, 게임 |

## DNS: 도메인 이름의 전화번호부

### DNS란 무엇인가

DNS(Domain Name System)는 사람이 읽기 쉬운 도메인 이름(`example.com`)을 IP 주소(`93.184.216.34`)로 변환하는 시스템입니다.

### DNS 조회 과정

브라우저에서 `https://example.com`을 입력하면 다음 과정이 일어납니다:

```
1. 브라우저 캐시 확인
2. OS 캐시 확인 (/etc/hosts 포함)
3. 로컬 DNS 리졸버(ISP)에 질의
4. 루트 네임서버 → TLD 네임서버(.com) → 권한 있는 네임서버 순으로 조회
5. IP 주소 반환 후 캐시 저장 (TTL 기준)
```

### 주요 DNS 레코드 타입

```
A     → 도메인을 IPv4 주소로 매핑        example.com → 93.184.216.34
AAAA  → 도메인을 IPv6 주소로 매핑
CNAME → 도메인을 다른 도메인으로 매핑    www → example.com
MX    → 이메일 서버 지정
TXT   → 텍스트 데이터 (SPF, DKIM 등)
NS    → 네임서버 지정
```

### TTL과 배포의 관계

DNS 레코드에는 **TTL(Time To Live)** 값이 있어, 이 시간 동안 캐시가 유지됩니다. 서버 주소를 변경하는 배포를 앞두고 있다면:

1. 배포 24~48시간 전에 TTL을 짧게(60초) 설정
2. 배포 후 새 IP로 변경
3. 전파 완료 후 TTL을 다시 길게 복구

## HTTP/HTTPS: 웹 통신의 언어

### HTTP 메서드와 상태 코드

```
GET    /posts          → 목록 조회
POST   /posts          → 새 리소스 생성
PUT    /posts/1        → 전체 수정
PATCH  /posts/1        → 부분 수정
DELETE /posts/1        → 삭제
```

자주 보게 되는 HTTP 상태 코드:

| 코드 | 의미 |
|------|------|
| 200 OK | 성공 |
| 201 Created | 생성 성공 |
| 301 Moved Permanently | 영구 리다이렉트 |
| 304 Not Modified | 캐시 유효 (변경 없음) |
| 400 Bad Request | 클라이언트 오류 |
| 401 Unauthorized | 인증 필요 |
| 403 Forbidden | 권한 없음 |
| 404 Not Found | 리소스 없음 |
| 500 Internal Server Error | 서버 오류 |

### HTTPS와 TLS 핸드셰이크

HTTPS는 HTTP에 TLS(Transport Layer Security) 암호화를 더한 프로토콜입니다. TLS 핸드셰이크는 대략 다음 순서로 이루어집니다:

```
1. 클라이언트 → 서버: 지원하는 TLS 버전·암호화 방식 목록 전송
2. 서버 → 클라이언트: 선택한 방식 + 인증서(공개키 포함) 전송
3. 클라이언트: 인증서 유효성 검증 (CA 체인 확인)
4. 클라이언트 → 서버: 대칭키 협상 (Diffie-Hellman 등)
5. 이후 대칭키로 암호화 통신 시작
```

TLS 1.3부터는 핸드셰이크가 1-RTT(이전 연결이 있으면 0-RTT)로 줄어들어 성능이 크게 향상됐습니다.

## 실무에서 바로 쓰는 네트워크 디버깅 도구

### curl로 HTTP 요청 테스트

```bash
# 기본 GET 요청
curl https://api.example.com/users

# 헤더 포함 POST 요청
curl -X POST https://api.example.com/users \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{"name": "Alice"}'

# 응답 헤더 확인
curl -I https://example.com

# 상세 디버그 출력 (TLS 핸드셰이크 포함)
curl -v https://example.com
```

### nslookup·dig으로 DNS 조회

```bash
# 도메인의 A 레코드 조회
nslookup example.com

# dig으로 더 자세한 DNS 정보 확인
dig example.com

# 특정 DNS 서버를 통해 조회 (8.8.8.8 = Google DNS)
dig @8.8.8.8 example.com

# TTL 확인
dig example.com +ttlid
```

### traceroute로 경로 추적

```bash
# 패킷이 목적지까지 거치는 모든 라우터 확인
traceroute example.com   # macOS/Linux
tracert example.com      # Windows
```

## 핵심 정리

| 개념 | 핵심 포인트 |
|------|-------------|
| TCP | 3-way 핸드셰이크로 신뢰성 보장, 첫 연결에 지연 발생 |
| UDP | 빠르지만 신뢰성 없음, 스트리밍·DNS에 활용 |
| DNS | 도메인 → IP 변환, TTL로 캐시 관리 |
| HTTP | 상태 코드와 메서드 숙지, 무상태(Stateless) 프로토콜 |
| HTTPS | TLS로 암호화, 인증서 체인 검증 |

네트워크는 한 번에 모두 외울 필요가 없습니다. `curl`로 API 테스트하다 헤더를 살펴보고, DNS 전파가 느릴 때 TTL을 확인하고, 느린 첫 요청을 보며 TCP 핸드셰이크를 떠올리는 식으로 실무 경험과 개념을 연결하다 보면 자연스럽게 체득됩니다. 네트워크를 이해한 개발자는 문제가 생겼을 때 어디서부터 살펴야 할지 알고 있기 때문에 훨씬 빠르게 해결책을 찾아냅니다.
